# 性能调优设计文档（P0 → P2）

> 版本：v1.0 ｜ 日期：2026-09-16 ｜ 对应代码：`logger.h` / `logger.cpp` / `tests/benchmark.cpp`
>
> 本文档按「原实现缺点 → 优化方案 → 优化收益」的结构，记录本次性能调优的全部改动、实测数据与副作用。

---

## 一、背景与基线

### 1.1 项目定位

本项目是一个基于 **双缓冲 + 单后台线程批量写盘** 的 C++11 异步日志库：
- 业务线程（前端）只做「格式化 + 加锁拷贝进缓冲区」，不触发磁盘 I/O
- 后台线程（消费者）把满缓冲区批量写入磁盘

### 1.2 优化前实测基线（VM：8 核 / 7.7GB / VMware 虚拟盘，GCC 11.4，-O2）

| 场景 | 吞吐 | 延迟 |
|---|---|---|
| 单线程（10 万条） | 11,942 条/秒 | 平均 83.74μs/条 |
| 10 线程（50 万条） | 25,496 条/秒（修正口径） | P50 110μs / P99 3.9ms / Max 31ms |
| 50 线程压力（100 万条） | 34,003 条/秒（修正口径） | 零丢弃 |
| 级别过滤热路径 | 全过滤 1.16 亿条/秒 | — |

> 注：上表为「修正统计口径后」的数据。原 benchmark 存在跨组累计统计 bug，详见 3.1 节。

### 1.3 瓶颈定位方法（先测量，再优化）

优化前通过 **分层对照实验** 定位瓶颈，而不是凭经验猜测：

1. **磁盘能力验证**：`dd if=/dev/zero of=/tmp/t bs=1M count=1024 conv=fdatasync`
   → 实测 VM 真实落盘带宽约 **32 MB/s**（O_DIRECT 瞬时 270MB/s 为 VMware 写缓存假象）
2. **纯前端对照**：输出到 `/dev/null`，隔离磁盘
   → 见新增 Benchmark 6
3. **长度扫描**：消息 10B→2000B，观测吞吐与带宽变化趋势（Benchmark 3）

**结论**：单线程 83.7μs/条 中，**ostringstream 前端格式化占绝对主导**；后台消费能力（32MB/s ÷ ~84B/条 ≈ 38 万条/秒）远高于前端产生速率。前端才是第一瓶颈。

## 三、P0：基准测试修正（原缺点 → 优化 → 收益）

### 3.1 统计口径 bug

**原实现缺点**：
1. Benchmark 2/4 的吞吐用 `stats.totalLogs`（**跨组累计不清零**）除以本组时间：
   - B2 报告 30,595 条/秒，实际本组仅 50 万条 → 真实 25,496（虚高 20%）
   - B4 报告 66,305 条/秒，实际本组仅 100 万条 → 真实 34,003（虚高 95%）
2. Benchmark 2/4 的带宽同样使用累计 `bytesWritten`，混入了上一组的写入量

**优化**：
- 吞吐改用本组实际日志数 `numThreads × logsPerThread`
- 带宽改用「测试开始/结束的 `bytesWritten` 差值」
- 新增 **Benchmark 6：纯前端吞吐（输出到 `/dev/null`）**，用于与落盘版本对照，回答「瓶颈在前端还是磁盘」

**收益**：所有报告数字变为真实、可复现、可写入简历的量级；B6 提供前端独立基准，方便后续任何优化直接对比。

## 四、P1：自研 LogStream + 时间戳缓存（核心改动）

### 4.1 原实现缺点

原 `LogStream` 基于 `std::ostringstream`，每条日志经历：

| 步骤 | 开销 | 实测占比（83.7μs 基准） |
|---|---|---|
| 构造 `ostringstream`（内部 stringbuf **堆分配**） | 堆分配 + locale 初始化 | ~15μs（18%） |
| 时间戳：`localtime_r` + `std::put_time` + `setw/setfill` 操纵符 | 每条日志一次，最昂贵 | ~30μs（36%） |
| 多次 `operator<<` 流插入（**虚函数调用** + 数字格式化走 locale 分支） | 5~8 次/条 | ~15μs（18%） |
| 析构 `stream_.str()`（**又一次堆分配 + 全量拷贝**） | 多余中间层 | ~12μs（14%） |
| `append()` 锁 + memcpy | 设计正确，保留 | ~8μs（10%） |

> 即：**每条日志 ≥2 次堆分配 + 多次虚调用 + 一次冗余全量拷贝**，单条固定开销高达 ~70μs。

### 4.2 优化方案

**（1）自研定长缓冲 `LogStream`（参考 muduo 设计）**
- 栈上 `FixedBuffer<16KB>` 成员数组：**零堆分配**
- `operator<<` 直接写入定长缓冲；整数用手工倒序转换（避开 iostream 虚函数与 locale），`double` 用 `snprintf("%.6g")`
- 析构直接提交缓冲指针，**消除 `str()` 中间 std::string 拷贝**
- 支持：`bool/char/短整型/int/unsigned/long/long long/double/float/const char*/std::string`

**（2）秒级时间戳缓存**
- `thread_local` 缓存秒级时间字符串（`"2026-09-16 12:00:00."`），**每秒最多一次 `localtime_r + strftime`**
- 毫秒由时间戳取模后**手工补零**（替代 `setfill/setw` 操纵符）
- 一次 `system_clock::now()` 同时取秒与毫秒

### 4.3 收益（实测，VM 同环境）

| 指标 | 优化前 | 优化后（4 次实测中位数） | 提升 |
|---|---|---|---|
| 单线程吞吐 | 11,942 条/秒 | **1,423,117 条/秒**（105~163 万） | **119.1x** |
| 单线程平均延迟 | 83.74μs | **0.74μs**（0.61~0.95） | **113.2x** |
| 10 线程吞吐（修正口径） | 25,496 条/秒 | **463,084 条/秒**（43~57 万） | **18.2x** |
| 10 线程 P50 延迟 | 110.20μs | **2.07μs**（1.95~2.17） | **53.2x** |
| 10 线程 P99 延迟 | 3,899μs | 414μs（356~448） | 9.4x |
| 50 线程吞吐（修正口径） | 34,003 条/秒 | **567,965 条/秒**（41~70 万） | **16.7x** |
| 50 线程带宽 | 11.73 MB/s | 48.9 MB/s（35~61） | 4.2x |
| 纯前端吞吐（B6，新增） | — | **2,322,149 条/秒**（205~284 万，0.44μs/条） | 新增基准 |

> **口径**：VM 共享宿主资源，单次测量波动可达 ±40%（纯 CPU 场景），上表为同环境连续 **4 次实测的中位数**（括号内为波动范围）；可用 `./bench_median.sh` 复测。

- 全部 **10/10 单元测试通过**，功能零回归
- 50 线程压力 100 万条 **零丢弃**（背压保护保持有效）

## 五、P2：工程化完善（安全性与可观测性）

### 5.1 fsync 持久化策略开关

**原实现缺点**：后台线程 `fwrite` 后不落盘（数据在内核页缓存），进程崩溃/断电可能丢失最近数秒日志——**没有选择权**。

**优化**：新增 `setFsyncOnFlush(bool)`（运行中可调用，原子开关）：
- `false`（默认）：性能优先，依赖内核异步回写，与原有行为一致
- `true`：每次后台 flush 后 `fflush + fsync` 强制落盘，崩溃最多丢失「当前未 flush 的缓冲」，换取数据安全

**收益**：同一份代码可适配「性能敏感」（默认）与「数据敏感」（关键业务）两种部署场景，且不牺牲默认路径性能。

### 5.2 队列积压预警

**原实现缺点**：后台消费跟不上时，只有积压超过 25 个缓冲区直接丢日志，**中间过程不可见**，问题发生时难以定位。

**优化**：积压超过 12 个缓冲时输出限频警告（每 100 次打印一次），提示「consumer falling behind」。

**收益**：可观测性提升；历史实测中 B3 大消息段（2KB 消息、磁盘跟不上）即触发过该警告（`13 buffers queued`），证明其在真实过载场景有效。丢日志兜底（>25）保持不变。

## 六、副作用与权衡（必须知晓）

| 副作用 | 影响 | 缓解/说明 |
|---|---|---|
| **单条日志上限 16KB**，超出截断 | 原 ostringstream 版无长度上限 | 日志库标准做法（muduo 亦如此）；若需更大可调 `LogStream::kMaxStreamSize` |
| **不支持 iostream 操纵符**（`setw/setprecision/setfill/hex...`） | `LOG_INFO << std::setw(3) << x` 不再编译 | 本仓库已同步移除 benchmark 中 2 处用法；自定义格式请改为手工拼接 |
| **不支持用户自定义类型的 `operator<<`** | 自定义结构体无法直接流式输出 | 可先格式化为 `std::string` 再输出 |
| **`double` 固定 `%.6g`**（6 位有效数字） | 无法运行时调整精度 | 与 iostream 默认精度一致；需要更多位数请手动 `snprintf` 后输出 |
| **时间戳缓存为 thread_local，跨秒刷新** | 毫秒精度不受影响；秒级部分缓存 1 秒内一致 | 与真实时间最多差 1 秒边界，日志场景可接受 |
| **16KB 栈缓冲** | 每条日志构造在栈上占 16KB | 日志调用通常为叶函数；深递归+大栈函数场景注意栈使用 |

## 七、后续优化方向（未实施）

1. **thread_local 无锁前端**：每线程独立缓冲 + 原子入队，消除 `append()` 全局锁竞争——高并发（>50 线程）场景的下一步。当前 50 线程吞吐中位数 56.8 万条/秒已接近后台单线程消费上限，继续加线程收益有限，需配合多消费者。
2. **后台多线程消费**：单后台线程写盘是当前瓶颈上限（48.9MB/s 中位数已超磁盘裸落盘 32MB/s，受益于页缓存）。若磁盘升级为 SSD/NVMe，可考虑多消费者。
3. **文件描述符直写**：`fwrite` 换 `write()` 系统调用，减少 stdio 一层缓冲拷贝（当前 4MB 大块下收益有限，优先级低）。
4. **日志压缩/抽样**：超高速率下可选压缩或采样，属于功能级扩展。

---

## 八、结论

- **瓶颈定位**：通过「dd 磁盘验证 + /dev/null 前端对照 + 长度扫描」三层实验，确认单/低并发瓶颈在前端 `ostringstream` 固定开销，而非磁盘。
- **核心优化**：零堆分配定长缓冲 `LogStream` + 秒级时间戳缓存，消除每条日志 2 次堆分配、5~8 次虚调用与 1 次冗余拷贝。
- **实测结果**（4 次中位数）：单线程 **119 倍**（1.2 万 → 142 万条/秒）、10 线程 P50 延迟 **53 倍**（110μs → 2.07μs）、50 线程 **17 倍**（3.4 万 → 56.8 万条/秒）、纯前端 232 万条/秒、全过滤 2.67 亿条/秒，10/10 单元测试通过、零丢弃。
- **遗留边界**：16KB 单条上限、无 iomanip/自定义类型支持、磁盘落盘 ~32MB/s 为环境硬顶（fsync 开启时）。
